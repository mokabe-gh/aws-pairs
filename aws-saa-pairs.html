アプリケーション統合

SQS/SNS

SQS（Simple Queue Service）
メッセージを一時的にため込む行列（キュー）。送信側が投げ込み、受信側が自分のペースで取りに来る（プル型）。処理が終わると削除され、そのメッセージは消える。標準キュー（順序保証なし・最低1回配信）とFIFOキュー（順序保証・重複排除）がある。
SNS（Simple Notification Service）
トピックに発行された1件のメッセージを、登録済みの全宛先へ一斉配信する同報放送（プッシュ型）。宛先はLambda、SQS、HTTPエンドポイント、メール、SMSなど。受信側が受け取れなければ基本的に失われる。

頻出構成：SNS＋SQSのファンアウト。1つのトピックに複数のキューをぶら下げ、同報しつつ各処理系がバッファを持つ。

処理速度の差を吸収したい・急増しても取りこぼしたくない → SQS。1つのイベントを複数システムへ同時通知 → SNS。

SNS/EventBridge

SNS
宛先の数と速さに強い同報。低遅延で大量のサブスクライバーへ配る。
EventBridge
イベントの中身（JSON）の条件でルールに一致したものだけを流す振り分け配電盤。AWSサービスのイベント、cron式のスケジュール実行、SaaS（Datadog等）からのイベントを扱える。配信まで1秒前後の遅延がある。

定期実行・AWSイベント起点・内容でフィルタ → EventBridge。多数の宛先へとにかく速く同報 → SNS。

SQS/Kinesis

SQS
読んだら消える消費モデル。タスクを1回ずつ確実にさばく。
Kinesis Data Streams
流れ続けるデータを一定期間（既定24時間、最大365日）保持し、複数のアプリが同じデータを何度でも読めるストリームモデル。シャード単位で順序が保証される。

複数の分析系が同じデータを別々に読む・巻き戻して再処理・順序が重要 → Kinesis。1件を1回だけ処理 → SQS。

Kinesis Data Streams/Data Firehose

Data Streams
シャードを自分で管理し、独自のリアルタイム処理コードを動かす。データを保持し再読み込みできる。
Data Firehose
受け取ったデータをバッファしてS3・Redshift・OpenSearch・Splunkへ自動配信するフルマネージドの配送路。保持はせず通過するだけ。Lambdaで途中変換が可能。

カスタム処理・保持が必要 → Data Streams。S3等へ置くだけ・運用したくない・数十秒の遅延を許容 → Firehose。

Kinesis/MSK

Kinesis
AWS独自のストリーミング基盤。
MSK（Managed Streaming for Apache Kafka）
Kafkaをそのままマネージドで動かす。既存のKafkaアプリをコード変更なしで移せる。

問題文に「Kafka」の一語があれば即 MSK。

分析

Athena/Redshift

Athena
S3のファイル（CSV/JSON/Parquet等）にそのままSQLを投げるサーバーレスのクエリエンジン。スキャンしたデータ量への課金で、Parquet変換・圧縮・パーティション分割でコストが下がる。
Redshift
データを取り込んで保持する列指向のデータウェアハウス。クラスターを持ち、継続的に大量のクエリを高速で回す。SpectrumでS3も直接参照できる。

たまに調べるだけ・データを動かしたくない・初期費用ゼロ → Athena。BIから毎日大量に分析・複雑な結合 → Redshift。

Glue/EMR

Glue
サーバーレスのETL。データカタログ（メタデータの台帳）とクローラ（スキーマ自動推定）を持ち、変換ジョブをSparkで実行する。クラスター管理は不要。
EMR
Hadoop / Spark / Hive / PrestoのクラスターをEC2上に立てて自分で制御する。細かいチューニングやスポットでの大幅なコスト削減ができる。

サーバー管理をなくしたい・カタログが欲しい → Glue。バージョンや設定を制御したい・既存のHadoop資産 → EMR。

Glue/DMS

Glue
データの形を変える（変換する）処理。
DMS（Database Migration Service）
稼働中のDBを止めずに別のDBへ移行し、継続的にレプリケーション（CDC）する。異種DB間（Oracle→Aurora等）はSCTでスキーマ変換を併用。

変換 → Glue。データベースの引っ越し・同期 → DMS。

OpenSearch/Kendra

OpenSearch Service
ログや文書のインデックスを作り、キーワードで高速検索・ダッシュボード可視化する（旧Elasticsearch）。
Kendra
機械学習ベースの企業内検索。「経費精算の締切は？」のような自然言語の質問に、社内文書から答えを返す。

ログ分析・全文検索基盤 → OpenSearch。質問に答えるナレッジ検索 → Kendra。

QuickSight/Managed Grafana

QuickSight
BIツール。売上や顧客データをグラフ・ダッシュボード化して業務部門が見る。SPICEという高速インメモリエンジンを持つ。
Managed Grafana
システムのメトリクス監視用の可視化。CloudWatch、Prometheus、OpenSearchなど多数のデータソースを1画面に集約する。

ビジネス指標 → QuickSight。運用・インフラ指標 → Grafana。

監視・ガバナンス

CloudWatch/CloudTrail/Config

CloudWatch
メトリクス（CPU使用率など）、ログ、アラーム、ダッシュボード。今どう動いているかを見る。
CloudTrail
AWS APIの呼び出し履歴。誰が・いつ・どのリソースに・何をしたかを記録する監査ログ。
Config
リソースの設定状態を記録し、変更履歴を残し、ルールへの準拠を継続評価する。非準拠時の自動修復も可能。

性能・ログ → CloudWatch。犯人探し・監査 → CloudTrail。設定の状態と準拠 → Config。

Trusted Advisor/Well-Architected Tool

Trusted Advisor
アカウント内の実リソースを自動スキャンし、コスト最適化・パフォーマンス・セキュリティ・耐障害性・サービスクォータの5観点で推奨を出す。全項目の利用にはビジネス以上のサポートプランが必要。
Well-Architected Tool
ワークロードについての質問に答えていく形式で、設計上のリスクを洗い出すレビューツール。リソースは見ない。

実リソースの自動チェック → Trusted Advisor。質問形式の設計レビュー → Well-Architected Tool。

Trusted Advisor/Compute Optimizer

Trusted Advisor
広く浅く5観点をチェックする。
Compute Optimizer
過去のCloudWatchメトリクスを機械学習で分析し、EC2・Auto Scalingグループ・EBS・Lambdaの最適なサイズを具体的に推奨する。

全体の健康診断 → Trusted Advisor。MLによるサイジング推奨 → Compute Optimizer。

Cost Explorer/Budgets/CUR

Cost Explorer
コストの傾向をグラフで可視化し、将来予測も出す。
Budgets
予算のしきい値を決め、超過・超過予測時にアラートを送る。アクション（SCP適用など）と連動できる。
CUR（Cost and Usage Report）
時間単位・リソース単位の最も詳細な生データをS3に出力する。AthenaやQuickSightで分析する前提。

見る → Cost Explorer。知らせる・止める → Budgets。細かく分析する → CUR。

Savings Plans/リザーブドインスタンス/スポット

Savings Plans
1年か3年、「1時間あたり◯ドル使う」とコミットして割引を得る。Compute Savings PlansはEC2・Fargate・Lambdaにまたがり、インスタンスファミリーやリージョンを変えても適用される。
リザーブドインスタンス（RI）
特定のインスタンスタイプ・リージョンにコミットして割引。ゾーンRIはキャパシティ予約も伴い、そのAZの枠を確保できる。
スポットインスタンス
余剰キャパシティを最大90%引きで使うが、2分前の通知で中断される可能性がある。

柔軟な割引 → Savings Plans。構成が固定・容量確保も必要 → ゾーンRI。中断に耐えるバッチ → スポット。

Organizations/Control Tower

Organizations
複数アカウントをまとめ、一括請求し、OU（組織単位）に分け、SCPで制限をかける部品。
Control Tower
Organizationsを土台に、ベストプラクティスに沿ったマルチアカウント環境（ランディングゾーン）を自動構築する。ガードレールとAccount Factory付き。

自分で組み立てる → Organizations。整った環境を自動セットアップ → Control Tower。

SCP/IAM/Config

SCP
組織内アカウントで「できることの上限」を定める。許可を与えるものではなく、上限を超える操作をさせない。ルートユーザーにも効く。
IAM
ユーザーやロールに権限を与える。
Config
違反した状態を後から見つける。

予防（させない） → SCP。許可 → IAM。発見（検出する） → Config。

セキュリティ

Parameter Store/Secrets Manager

Parameter Store（SSM）
設定値やパスワードを保存する。標準パラメータは無料。ローテーションの仕組みは自前で用意する。
Secrets Manager
有料だが、Lambdaによる自動ローテーションを標準機能として持ち、RDS・Redshift・DocumentDBと統合されている。

安価・ローテーション不要 → Parameter Store。自動ローテーション・RDS統合 → Secrets Manager。

KMS/CloudHSM

KMS
AWSマネージドの鍵管理。ほぼ全AWSサービスと統合され、暗号化がチェックボックス感覚で使える。キーの自動ローテーションあり。
CloudHSM
自分専用のハードウェアセキュリティモジュール。FIPS 140-2 レベル3準拠で、鍵はユーザーが完全に管理しAWSはアクセスできない。

簡単・統合が豊富 → KMS。専用HSM・FIPS 140-2 レベル3・AWSに鍵を触らせない・独自PKI → CloudHSM。

Cognito/IAM Identity Center

Cognito
アプリのエンドユーザー（顧客）向け。ユーザープールでサインアップ／サインイン、IDプールでAWSリソースへの一時的な権限を配る。SNSログイン対応。
IAM Identity Center（旧AWS SSO）
従業員向け。Active Directoryや外部IdPと連携し、複数AWSアカウントへのシングルサインオンを提供する。

アプリの顧客 → Cognito。従業員のAWSアクセス → IAM Identity Center。

GuardDuty/Inspector/Macie/Detective/Security Hub

GuardDuty
CloudTrail・VPCフローログ・DNSログを機械学習で分析し、不審な通信やクレデンシャル悪用を検知する。エージェント不要で有効化するだけ。
Inspector
EC2・ECRのコンテナイメージ・Lambdaを対象に、既知の脆弱性（CVE）をスキャンする。
Macie
S3内のデータを走査し、個人情報やクレジットカード番号などの機密データを発見する。
Detective
検知された事象について関連ログを自動でつなぎ、根本原因を調査する。
Security Hub
各サービスや他社製品の検出結果を集約し、セキュリティ基準への準拠状況をスコア表示する。

脅威検知／脆弱性／S3の機密データ／調査／集約 の5語で切り分ける。

WAF/Shield/Network Firewall

WAF
HTTPリクエストの中身を見て、SQLインジェクション、XSS、特定IP、地理、レート超過をブロックする（L7）。CloudFront・ALB・API Gateway・AppSyncに関連付ける。
Shield
DDoS対策。Standardは無料で自動適用（L3/L4）。Advancedは有料で、専門チームの対応と急増した料金の補填が付く。
Network Firewall
VPC全体を対象としたステートフルなファイアウォール。アウトバウンドのドメインフィルタリングや侵入防止に使う。

L7のリクエスト内容 → WAF。攻撃の物量（DDoS） → Shield。VPCのネットワーク全体・ドメインフィルタ → Network Firewall。

セキュリティグループ/ネットワークACL

セキュリティグループ
インスタンス（ENI）に付く。ステートフルで、戻りの通信は自動的に許可される。書けるのは許可ルールのみ。
ネットワークACL
サブネットに付く。ステートレスなので戻りの通信も明示的に許可が必要（エフェメラルポートに注意）。拒否ルールが書け、ルール番号の小さい順に評価される。

インスタンス・ステートフル・許可のみ → SG。サブネット・ステートレス・特定IPの遮断 → NACL。

ネットワーク

VPCピアリング/Transit Gateway/PrivateLink

VPCピアリング
2つのVPCを1対1で接続。推移的なルーティングは不可（A–B、B–Cを繋いでもA–Cは通信できない）。CIDRの重複は不可で、数が増えると接続数が爆発する。
Transit Gateway
多数のVPCとオンプレをつなぐハブ。推移的ルーティングが可能で、ルートテーブルで経路を分離できる。数千VPC規模に対応。
PrivateLink
VPC全体をつなぐのではなく、特定のサービスだけをENI経由で公開する。CIDRが重複していても使え、通信は一方向。

1対1で単純 → ピアリング。多対多のハブ・推移可 → TGW。サービス単位の公開・CIDR重複可 → PrivateLink。

CloudFront/Global Accelerator

CloudFront
世界中のエッジロケーションにコンテンツをキャッシュするCDN。HTTP/HTTPSが対象。OACでS3を非公開のまま配信できる。
Global Accelerator
2つの静的なAnycast IPを提供し、ユーザーを最寄りのエッジからAWS内部網経由で最適なリージョンへ運ぶ。キャッシュはしない。TCP/UDPに対応し、ヘルスチェック失敗時は即座に切り替わる。

キャッシュ・HTTP → CloudFront。静的IP・TCP/UDP・即時フェイルオーバー → Global Accelerator。

Direct Connect/Site-to-Site VPN

Direct Connect
AWSへの専用線。帯域が一貫しレイテンシが安定するが、開通まで数週間以上かかり高価。単体では暗号化されない（VPN併用可）。
Site-to-Site VPN
インターネット上にIPsecトンネルを張る。即日開通・安価だが、帯域とレイテンシはインターネット次第。

一貫した帯域・低レイテンシ・構築に数週間 → DX。即日・安価・インターネット経由 → VPN。DXのバックアップにVPNを併用する構成も頻出。

Client VPN/Site-to-Site VPN

Client VPN
在宅勤務者などの個人の端末からVPCへ接続する（OpenVPNベース）。
Site-to-Site VPN
拠点のルーターとAWSの間をトンネルで結び、オフィスごと接続する。

個人の端末から → Client VPN。拠点ネットワークから → Site-to-Site VPN。

ALB/NLB

ALB
L7（HTTP/HTTPS）。URLパス・ホスト名・ヘッダーによる振り分け、Lambdaをターゲットにできる、WebSocket対応、認証機能あり。
NLB
L4（TCP/UDP/TLS）。超低レイテンシで毎秒数百万リクエストを処理。静的IP／Elastic IPを持て、PrivateLinkのフロントに使える。

パスやホストで振り分け・Lambda → ALB。静的IP・非HTTP・極端な性能要求・PrivateLink → NLB。

Route 53 レイテンシールーティング/Global Accelerator

Route 53 レイテンシールーティング
DNSの応答で最寄りリージョンへ導く。TTLの間は古い宛先がクライアントにキャッシュされるため、障害時の切替が遅れる。
Global Accelerator
Anycast IPなのでDNSの再解決を待たず、経路の切替が即座に効く。

DNSで振り分け（TTLの影響あり） → Route 53。DNSキャッシュが問題・即座に切替 → Global Accelerator。

ストレージ

S3/EBS/EFS

S3
オブジェクトストレージ。HTTP API経由でアクセスし容量は無制限。OSからドライブとしてマウントする用途には向かない。
EBS
EC2に接続するブロックストレージ（仮想ハードディスク）。原則1インスタンスに1つ、同一AZ内のみ。スナップショットはS3に保存される。
EFS
NFSの共有ファイルシステム。複数のEC2から同時にマウントでき、複数AZにまたがる。容量は自動で伸縮。

オブジェクト・API → S3。1インスタンスのディスク・単一AZ → EBS。複数インスタンスで共有・NFS → EFS。

EFS/FSx for Windows File Server

EFS
Linux向けのNFS共有ファイルシステム。
FSx for Windows File Server
SMBプロトコル、Active Directory統合、Windowsアプリ向けの共有ファイルサーバー。

Linux・NFS → EFS。Windows・SMB・AD → FSx for Windows。高性能計算なら FSx for Lustre。

DataSync/Storage Gateway

DataSync
オンプレとAWS間で大量のファイルを高速かつスケジュール的にコピー・同期する。移行が終われば役目を終える。
Storage Gateway
オンプレのサーバーからAWSのストレージをローカルのように使い続けるための仮想アプライアンス。File（NFS/SMB→S3）、Volume（iSCSI）、Tape（仮想テープ→Glacier）の3種。よく使うデータはローカルにキャッシュされる。

移行・同期（一方向のコピー） → DataSync。継続的なハイブリッド利用 → Storage Gateway。

DataSync/Snow Family

DataSync
十分な回線があるときのオンライン転送。
Snow Family
物理デバイスにデータを入れて輸送する。Snowcone（小型）、Snowball Edge（テラ〜ペタ級、現地での処理も可能）。

オンライン転送 → DataSync。回線が細い・PB級のオフライン輸送 → Snow。

Storage Gateway/Outposts

Storage Gateway
ストレージだけをハイブリッド化する仮想アプライアンス。
Outposts
AWSが設計したラックそのものを自社データセンターに設置し、EC2・EBS・S3・RDSなどをオンプレ内で動かす。

ストレージだけ → Storage Gateway。コンピュートも含めてオンプレにAWSを設置 → Outposts。

Outposts/Local Zones/Wavelength

Outposts
自社施設内にAWSのラックを置く。データ主権や工場内の低レイテンシ要件に対応。
Local Zones
AWSが大都市近郊に置く小規模拠点。自社設備は不要で、その都市のユーザーに低レイテンシで届く。
Wavelength
通信キャリアの5Gネットワーク内にAWSを配置。モバイル端末からの超低レイテンシ用途。

自社施設 → Outposts。都市部のAWS拠点 → Local Zones。5Gキャリア網内 → Wavelength。

移行

MGN/DMS/VMware Cloud on AWS

MGN（Application Migration Service）
既存サーバーのブロックレベルレプリケーションを取り、そのままEC2として起動させるリフト＆シフト用ツール。
DMS
データベースを止めずに移行・レプリケーションする。
VMware Cloud on AWS
AWS上にVMware環境（vSphere/vSAN/NSX）を構築し、既存の仮想マシンを変換せずに移す。運用手法を変えたくない場合に使う。

サーバーをEC2化 → MGN。DBの移行 → DMS。VMwareのまま動かす → VMware Cloud on AWS。

コンピュート

ECS/EKS

ECS
AWS独自のコンテナオーケストレーション。タスク定義とサービスというシンプルな構成で、AWSサービスとの統合が容易。
EKS
マネージドKubernetes。運用は複雑だが移植性が高い。

AWS独自・シンプル → ECS。問題文に「Kubernetes」「k8s」「既存のマニフェスト」 → EKS。

EKS/EKS Anywhere/EKS Distro

EKS
AWS上のマネージドKubernetes。
EKS Anywhere
オンプレの自社ハードウェア上でKubernetesを運用する。AWSのサポートとツールが付く。
EKS Distro
EKSが使うKubernetesディストリビューションのソフトウェア配布のみ。運用は完全に自己責任。

AWS上 → EKS。オンプレで自分で運用（サポート付き） → EKS Anywhere。ソフトウェア配布のみ → EKS Distro。

Lambda/Fargate/EC2

Lambda
イベント駆動の関数実行。最大15分、メモリ最大10GB。実行時間課金で、リクエストがなければ費用ゼロ。
Fargate
サーバーレスのコンテナ実行環境（ECS/EKSの起動タイプ）。実行時間の制限がなく、常時稼働の長いプロセスも動かせる。
EC2
OSレベルの制御、特殊なライセンス要件、GPUなど特殊インスタンスが必要な場合。

15分以内・イベント駆動 → Lambda。コンテナ・長時間・サーバー管理なし → Fargate。OSの制御が必要 → EC2。

API Gateway/AppSync/ALB

API Gateway
REST/HTTP/WebSocket APIの入口。認証、スロットリング、キャッシュ、ステージ管理、使用量プランなどのAPI管理機能を備える。
AppSync
GraphQLのマネージドサービス。必要なフィールドだけ取得でき、サブスクリプションによるリアルタイム更新やモバイルのオフライン同期に強い。
ALB
単純にHTTPリクエストを複数のターゲットへ分散するだけ。API管理機能はない。

REST・APIキー・レート制限 → API Gateway。GraphQL・リアルタイム同期 → AppSync。単純なHTTP負荷分散 → ALB。

データベース

RDS マルチAZ/リードレプリカ

マルチAZ
別AZのスタンバイへ同期レプリケーション。可用性のための仕組みで、スタンバイには読み書きともにアクセスできない。障害時は自動でフェイルオーバーし、エンドポイントが切り替わる。
リードレプリカ
非同期レプリケーション。読み取りクエリを分散させる性能のための仕組み。別リージョンにも作成でき、独立したDBへ昇格できる。

可用性（同期・読み取り不可） → マルチAZ。性能（非同期・読み取り可） → リードレプリカ。両方求められたら両方使う。

Aurora/Aurora Serverless

Aurora
MySQL/PostgreSQL互換。データを3AZに6つコピーし、最大15のリードレプリカを持てる。
Aurora Serverless v2
負荷に応じて容量が自動で伸縮する。使っていない時間の費用を抑えられる。

安定した負荷 → プロビジョンド Aurora。断続的・予測不能な負荷（開発環境など） → Aurora Serverless。

DynamoDB Accelerator（DAX）/ElastiCache

DAX
DynamoDB専用のインメモリキャッシュ。読み取りをマイクロ秒単位に短縮する。DynamoDBとAPI互換なのでアプリの改修がほぼ不要。
ElastiCache
汎用のキャッシュ。RDSのクエリ結果、セッション情報の共有、リーダーボードなどに使う。アプリ側にキャッシュ読み書きのロジックを実装する必要がある。

DynamoDBが遅い・コードは変えたくない → DAX。汎用キャッシュ・セッション共有 → ElastiCache。

ElastiCache Redis/Memcached

Redis
レプリケーション、マルチAZ自動フェイルオーバー、永続化、Pub/Sub、Sorted Set（ランキング）などの高度なデータ型を持つ。
Memcached
単純なKey-Valueキャッシュ。マルチスレッドで大きなノードを使い切れるが、永続化もレプリケーションもない。

HA・永続化・レプリケーション・ランキング → Redis。シンプル・マルチスレッド → Memcached。

DocumentDB/DynamoDB/Keyspaces/Neptune

DocumentDB
MongoDB互換のドキュメントDB。
DynamoDB
サーバーレスのKey-Value／ドキュメントDB。1桁ミリ秒、無制限のスケール。
Keyspaces
Apache Cassandra互換。
Neptune
グラフDB。ソーシャルの友達関係、不正検知、レコメンドなど「つながり」の検索。

MongoDB／Key-Value／Cassandra／グラフ・関係性 の語で一意に決まる。

AIサービス

Rekognition/Textract/Comprehend

Rekognition
画像・動画の解析。物体検出、顔認識・顔比較、不適切コンテンツの検出。
Textract
文書からのテキスト抽出。単純なOCRを超えて、表やフォームの項目と値を構造として取り出せる。
Comprehend
自然言語処理。感情分析、エンティティ抽出、キーフレーズ、言語判定。医療文書向けはComprehend Medical。

画像の物や顔 → Rekognition。文書から表やフォームを抽出 → Textract。テキストの意味・感情 → Comprehend。
